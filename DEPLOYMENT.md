# ZUVRE — Deployment Guide (Phase 0)

Target: `Kenovate-source/ZUVRE-platform` on GitHub → a **new** Vercel project.

## 1. What This Repository Contains

A pnpm + Turborepo monorepo:

```
zuvre/
  apps/web/            The deployable Next.js app (this is what Vercel builds)
  packages/db/          Prisma schema + scoped Postgres client
  packages/capability-sdk/   Capability contract + registry
  packages/ai-gateway/  Provider-agnostic AI routing (Anthropic adapter included)
  packages/auth/        Sessions, RBAC, password hashing, owner-audit wrapper
  packages/ui/          Design tokens (Solmere / Duskmere themes)
  docs/                 Product/architecture/brand documentation + ADRs
```

Everything in `apps/web` and `packages/*` is real source code (see
`STATUS.md` for exactly what's implemented vs. designed-only — that hasn't
changed since Phase 0 was first delivered; this pass is a deployability
fix only, not a feature pass).

## 2. Vercel Project Settings

| Setting | Value |
|---|---|
| **Root Directory** | `apps/web` |
| **Framework Preset** | Next.js (auto-detected) |
| **Build Command** | leave as Vercel's default (`next build`, auto-invoked through Turborepo's monorepo detection — do not override manually) |
| **Install Command** | leave as Vercel's default (`pnpm install`, run from the repo root once Root Directory + a committed lockfile tell Vercel this is a workspace) |
| **Output Directory** | leave as Vercel's default (`.next` — Next.js's standard output, auto-detected, do not set manually) |

Vercel's Turborepo/pnpm-workspace auto-detection handles all of the above
correctly **once a real `pnpm-lock.yaml` is present at the repo root** —
that lockfile is the one thing this repository is still missing (see §6).
Do not hand-enter a custom Build/Install/Output Directory unless a future
build tells you otherwise; overriding these manually is what tends to
break Vercel's monorepo detection, not fix it.

## 3. Environment Variables Currently Required

Set these in the Vercel project's **Settings → Environment Variables**:

| Variable | Required for | Notes |
|---|---|---|
| `DATABASE_URL` | Prisma client at build+runtime | Postgres connection string (Vercel Postgres, Neon, Supabase, Railway all work) |
| `AUTH_SECRET` | Session signing (`packages/auth`) | 32+ random bytes |
| `ANTHROPIC_API_KEY` | The `ai.chat` capability | Without it, the app still builds and runs; `ai.chat` fails cleanly at call time via the provider's `isConfigured()` guard |

Everything else in `.env.example` is optional for Phase 0 (unused
provider keys, observability DSN, etc. — see the file's comments).

`DATABASE_URL` must be set **before the first deploy** — `packages/db`'s
`build` script runs `prisma generate` (see §5, item 2), which reads the
schema but does **not** need a live database connection to succeed;
however Next.js's build will fail if `packages/db/src/client.ts` is
evaluated at build time without `DATABASE_URL` defined in the environment
(Prisma throws on `new PrismaClient()` construction without it), so set it
regardless of whether you've provisioned/migrated the database yet.

## 4. Files That Must Be Committed to GitHub

All of these — nothing in this list is optional or auto-generated by Vercel:

- `package.json`, `pnpm-workspace.yaml`, `turbo.json`, `tsconfig.base.json`, `.npmrc`
- **`pnpm-lock.yaml`** — see §6, this is the one file you must add locally
- `.gitignore` (already excludes `node_modules/`, `.next/`, `.turbo/`, etc. — correct, do not commit those)
- `apps/web/**` (all source, config, and `package.json`)
- `packages/*/**` (all source, `package.json`, and `packages/db/prisma/schema.prisma`)
- `docs/**` (documentation — not required for the build to succeed, but part of the deliverable)

Do **not** commit: `node_modules/`, `.next/`, `.turbo/`, `.env` (only
`.env.example` should be committed).

## 5. What Was Fixed This Pass

1. **`.npmrc`** (new, root) — `auto-install-peers=true`,
   `strict-peer-dependencies=false`, to prevent pnpm's peer-dependency
   resolution from stalling the install on Vercel's CI.
2. **`packages/db/package.json`** (modified) — added a `"build": "prisma
   generate"` script, so Turborepo's own build graph
   (`turbo.json`'s `build` task already declares `"dependsOn": ["^build"]`)
   generates the Prisma client as part of building `@zuvre/db`, before
   `@zuvre/web` builds. This replaced an earlier root-level `postinstall`
   hook that ran `pnpm --filter @zuvre/db run generate` — that approach
   failed on Vercel with `prisma: command not found`, because a root
   `postinstall` lifecycle script fires mid-install, before
   `packages/db`'s own `prisma` devDependency binary is reliably linked
   into its `node_modules/.bin`. Turborepo's build graph runs strictly
   after install completes, inside each package's own directory, which is
   why it's the correct place for this step rather than an install-time
   hook. The root `package.json` no longer has a `postinstall` script.
3. **`packages/db/prisma/schema.prisma`** (modified) — removed a custom
   Prisma `generator client { output = ... }` path that didn't match the
   `import { PrismaClient } from "@prisma/client"` in
   `packages/db/src/client.ts`. Left in place, this would have caused a
   **second**, different build failure immediately after the lockfile
   issue was fixed. It's fixed now, before you hit it.

None of this changes ZUVRE's architecture, removes any functionality, or
touches anything outside the install/build chain.

## 6. What You Must Do Locally — Lockfile Generation

**This environment has no network access, so `pnpm-lock.yaml` could not be
generated here.** No lockfile is included in this ZIP. Do not accept a
`pnpm-lock.yaml` from any source that didn't run a real `pnpm install`
against the actual npm registry — a fabricated one will not match real
package resolutions and will fail or silently drift from what actually
gets installed.

Run this on a machine with internet access:

```bash
# 1. Unzip this deliverable, or clone your repo after pushing these files
cd zuvre

# 2. Match the pnpm version pinned in package.json's "packageManager" field
corepack enable
corepack prepare pnpm@9.0.0 --activate

# 3. Real install — this is what generates pnpm-lock.yaml
pnpm install

# 4. Sanity-check Prisma client generation (also runs automatically as part of `pnpm build`, via Turborepo)
pnpm --filter @zuvre/db generate

# 5. Sanity-check the full monorepo actually builds
#    (set DATABASE_URL and AUTH_SECRET in your shell or a local .env first)
pnpm build
```

If step 5 succeeds locally, the same install/build will succeed on Vercel
— it's the identical `pnpm install` → `pnpm build` chain, driven by the
same `pnpm-lock.yaml` you just generated.

Then:

```bash
git add pnpm-lock.yaml
git commit -m "chore: add pnpm-lock.yaml (generated with pnpm@9.0.0)"
git push
```

(The other three fixes — `.npmrc`, `package.json`, `schema.prisma` — are
already included in this ZIP; commit them alongside the lockfile if you
haven't already pushed them.)

## 7. After Pushing

Trigger a redeploy on the Vercel project (or just push — Vercel deploys on
push by default). With the lockfile present and Root Directory set to
`apps/web`, Vercel's install step will now find the workspace, install
`next` and every workspace package correctly, and the build should
proceed past the point it failed before.

I have not been able to verify this against a live Vercel build — this
environment cannot reach the internet, so I can't run `pnpm install` or
trigger a deployment myself. Please run §6's local steps and report back
either the successful `pnpm build` output or whatever error comes next,
and I'll continue from there.
